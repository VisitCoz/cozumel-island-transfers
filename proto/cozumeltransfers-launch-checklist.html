Putting Cozumel Transfers on the air

The code is finished and pushed. What is left is five things inside two dashboards — Netlify and Cloudflare — that I have no login for. None of them touch the site that is live and taking money today.

What we are building

Two front doors, one engine. Both brands sell the same transfer, take the same card through the same Stripe account, and land in the same inbox. Only the front of the house is duplicated.

Your five steps

Roughly twenty minutes. Steps 1–3 are Netlify, step 4 is Cloudflare, step 5 is telling me.

  1. Netlify → Add new site → Import an existing project

    Create a second site from the same repository

    Pick the same GitHub repo you already use — VisitCoz/cozumel-island-transfers. Netlify will let you add it twice; that is normal and it is what we want.

    On the build settings screen, the one field that matters:

    SettingWhat to put
    Branch to deploycozumeltransfers Not main. This is the single setting that keeps the two sites apart. If this says main, you have just deployed a second copy of the live site.
    Build commandleave empty There is no build step — the page is plain HTML.
    Publish directory. Netlify reads this from netlify.toml anyway; just don't override it.
    Site namesomething like cozumeltransfers Only decides the temporary *.netlify.app address. Cosmetic.

    Deploy it. It will go live on a something.netlify.app address straight away. Don't test a booking yet — the keys aren't in place, so it would fail.

  2. Netlify → the NEW site → Site configuration → Environment variables

    Copy across exactly these two, and no others

    A Netlify site starts with an empty set — nothing is inherited from the other one. Open the live site's variable list in a second tab and copy the values across. Don't paste any value into a message, a document or a chat, including to me; I only ever need the names.

    NameWhere its value comes from
    STRIPE_SECRET_KEY Copy the value from the live site, unchanged. Same Stripe account on purpose — it is what puts both brands' money in one balance and lets the one webhook handle both. Without it, the pay button returns an error instead of opening Stripe.
    SITE_URL Type it fresh: https://cozumeltransfers.org Do not copy the live site's value. This is the address Stripe sends the guest back to after she pays. Set wrong, she pays and then lands on the other brand's website, which looks like she has been handed off to a stranger.
    ⛔ Three that must stay UNSET on the new site

    STRIPE_WEBHOOK_SECRET — there is no webhook here. Setting it does nothing useful and invites someone to add one back.

    TEST_PRICE_USD and TEST_CURRENCY — these exist to charge $5 in pesos during a test. While either is set, every booking on the site charges the test amount. Leave them off, and when we do run a test booking, remember to remove them the same hour.

    🤔 One decision I need from you

    There are four more variables on the live site — two for the funnel log (FUNNEL_URL, FUNNEL_TOKEN) and two for the refusal log (REFUSALS_URL, REFUSALS_TOKEN). They feed the two Google Sheets that record where visitors drop off and who a rule turned away.

    If you copy them, both sites write into the same sheet and neither row says which site it came from — the two brands' numbers get blended and can't be pulled apart later. If you leave them out, the new site silently records nothing and the live site's figures stay clean.

    My recommendation: leave all four out for now. The new site has no traffic yet, so there is nothing to lose, and adding a site column later is a small job. Tell me if you'd rather have the data blended from day one.

  3. Netlify → the NEW site → Domain management → Add a domain

    Add cozumeltransfers.org as the custom domain

    Enter cozumeltransfers.org. Netlify will say the domain is registered elsewhere and offer to let you point it yourself — take that option. Do not let it move the nameservers to Netlify: the domain sits on Cloudflare and we want it to stay there, the same way the live site does.

    Netlify then shows you the DNS records it wants. Those are what step 4 is for.

    It will also ask whether www.cozumeltransfers.org should work. Tell me which you choose — if you want www to work, there is a one-line rule I need to add to the repo so the two addresses don't count as two separate websites to Google.

  4. Cloudflare → cozumeltransfers.org → DNS → Records

    Point the domain at the new site

    Add exactly what Netlify showed you on the previous screen. It is normally one record:

    TypeNameValueProxy
    CNAME @ the bare domain <your-site>.netlify.app the exact address Netlify gives you — copy it, don't retype it 🟠 Proxied the orange cloud ON, same as the live site

    If Netlify asks for an A record to an IP address instead, use that — follow what its screen says, not what this page guesses.

    ⚠️ Set SSL/TLS to Full (strict) before you test

    Cloudflare → SSL/TLS → Overview. If a fresh zone is left on Flexible, the browser and Netlify disagree about who is encrypting what and the page can redirect in a loop that looks exactly like a broken deploy. Match whatever the live zone is set to.

    Give the certificate a few minutes. A padlock warning in the first five minutes is normal; one that is still there after an hour is not.

  5. Message me

    Tell me it's up, and I'll run the test booking

    Send me the new address once it loads. I'll then walk a real booking end to end and confirm the four things that can only be checked once it is live: that the pay button reaches Stripe, that paying sends the guest back to cozumeltransfers.org and not the other domain, that the team email and the guest email both arrive, and that the booking carries its new site tag in Stripe so the manifest can tell the two brands apart.

    No card gets charged for real — we'll use the $5 test override and take it off the same hour.

Three things I could not fix from here

All three are decisions, not bugs. None of them stop the site going up, and none of them touch a price.

🚨 The confirmation email will say the other brand's name

Bookings from the new site are emailed by the old site's webhook, and that email template signs off "Cozumel Island Transfers" and links to the old domain. So a guest who books on Cozumel Transfers gets a receipt from a company she has never heard of — which reads like a scam to exactly the nervous first-time buyer this site is built for.

The fix is small and I have already laid the groundwork: every booking now carries a site tag saying which brand sold it, so the email can pick the right name and link. But that template lives on the live site's branch, so changing it changes the live site — I won't touch that without you saying go. Say the word and I'll do it before the test booking.

⚠️ Four supporting files still name the old site

llms.txt (what AI assistants read), sitemap.xml, robots.txt and the terms, privacy, 404 and meeting-point pages all still say "Cozumel Island Transfers" and point at the old domain. They were outside what you asked me to change, and two of them also hold the price list, which I was told to leave byte-for-byte alone.

Nothing breaks — the pages load and the prices are right. But an AI assistant reading the new site is told it is the old one. Half an hour of work whenever you want it.

⚠️ The share card image still has the old logo on it

When someone shares the new site on WhatsApp, the preview picture is the one made for the other brand, with its name burned into the image. Worth replacing before you push the new address anywhere. Same for the TripAdvisor rating in the page's hidden data: it belongs to the old listing, and Google may object to a review score attached to a different name.
